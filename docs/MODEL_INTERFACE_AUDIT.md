# Model, presentation and tool interface audit

**Audit baseline:** `origin/main` at `2c06eaf`, which merged M4c0 as PR #16, 2026-10-11. This is a design report, not an implemented interface. The audit branch is based on that merge and adds this document alone. No model, sampler, worker, archive, UI or test code was changed for this report.

The proposed full-width featured display is feasible **without rewriting a mathematical model or its worker**. For QM and Fields, it is principally a placement change around the existing `ToolDeck` definitions and `renderTool` switch. The other workspaces need small, model-specific presentation adapters first. A universal configuration array or one worker protocol for every future theory would erase real distinctions already present in the source.

## Reading map and conventions

This audit follows [AGENTS.md](../AGENTS.md), the [source guide](SOURCE_GUIDE.md), [specification](SPECIFICATION.md), [roadmap](ROADMAP.md), [decisions](DECISIONS.md), and the M0.5–M4c0 review notes. The numerical path is domain → model/action/reference → transition → worker-owned run/observables → snapshot/client → view. In particular, `src/models/` has no React dependency. `src/app/App.tsx` mounts five tabs, but tabs are presentation/session locations, **not** model IDs. “Update” below means an algorithmic operation, never physical time. A nominal local sweep is a count of site attempts; a direct draw replaces a whole configuration. A parameter segment always represents one target measure and one measurement cadence.

### Three levels of model selection

1. A **model family** fixes the state space, action or probability law, and the capabilities that its numerical implementation can support. Finite graph Ising is one family; its one-site, dimer and torus instances need no separate Ising energy or transition kernel.
2. A **concrete system** fixes a family’s geometry, boundaries and physical parameters. A four-spin periodic ring with specified bond weights and fields is a concrete graph-Ising system. Sampler, seed, warm-up and stride are numerical run settings on that system, not its topology or probability law.
3. A **named example** is a pedagogically selected concrete-system default, with a question/explanation and initial featured/gallery tools. Users can edit geometry size, couplings, fields and sampler where the model permits. An example name does not freeze its defaults or create a new numerical kernel. Multiple examples may share the same family and even the same topology with different couplings.

The existing `Model.kind`, `FieldSettings.model`, `Domain.id`, workspace hash and saved `source.workspace` are different concepts. A future catalog should give examples stable IDs without changing any of those existing serialized identities merely to improve navigation. An example may appear in several teaching perspectives or workspaces through presentation metadata. The mathematical implementation itself must not import or encode a fixed tab identity.

## Named examples and custom tiny graphs: feasibility

`src/domain/graph.ts` currently exports **seven** `graphPreset` values: `site`, `path`, `ring`, `square`, `star`, `complete` and `torus`. Except for `site`, each constructs **four** vertices. `GraphWorkspace` lists precisely those values in its geometry selector, and `isingPreset` supplies their default dimensionless weights. The separate `spin` model in `singleVariable.ts` is also a directly selectable one-spin model; it agrees mathematically with graph Ising on one site but has its own existing transition path and seeded history. Do not silently replace one with the other during a catalog migration. `validateDomain`, `validateIsing`, `exactIsing` and `isingTransition` work on one to four vertices and individually identified edges; `ising.test.ts` already exercises arbitrary two/three-spin graphs, parallel bonds and self-links. This is **numerical representability**, not a shipped named example or completed editor.

The visible catalog should show a short teaching progression first—single spin, dimer, frustrated triangle, periodic ring and 2×2 square—then progressively disclose other open/periodic, four-site and custom cases. Grouping by question and topology prevents the `spin`/`site` duplication and the impression that every sign or boundary variant is a new model family. Direct example selection should load defaults and show the model/system identity; subsequent parameter edits remain ordinary Apply operations. A named example can provide a default featured graph and relevant conditional/correlation cards without coupling the sampler to the gallery.

### Presence is not a zero coupling

For a **custom simple graph** with two to four vertices, offer the complete set of unordered distinct pairs (`n(n−1)/2`, at most six) as *available choices*. A small parameter list can give each pair an **enabled/present** control and a signed coupling input. A present edge with `K=0` remains a `Domain.edges` record with an ID, selectable/inspectable as such; a disabled edge is absent from the applied domain. Existing K4 zero-weight configurations therefore retain their six edge records and must not be silently reclassified as custom subgraphs. Conversely, deleting a custom edge must not be simulated by setting its coupling to zero. The distinction matters for topology, provenance and future link observables even when current Ising probabilities happen to agree.

Use canonical, stable pair IDs for newly created custom domains (for example `pair:v0:v1`) so enabling another pair does not renumber existing edges. Keep the enabled state in the **draft editor**, materialize the applied `Domain.edges` from it on Apply, and retain a draft weight for a temporarily disabled pair without treating that weight as an active interaction. Changing the applied presence set or vertex count changes `topologyKey` and must start a **new seeded session** under `SmallSystemsApp.applyGraph`/`SimulationRun.changeSettings` rules. Changing only an active coupling or site field keeps the topology and starts an isolated **parameter segment**, preserving current configuration/RNG. A zero-to-nonzero change on an already-present edge is such a parameter change. The distinction must be shown before Apply; selection and draft toggling consume no RNG.

Do not retrofit this canonical-ID scheme into existing `e0`… preset domains or reinterpret old scalar configuration URLs and archived graph captures. `GraphWorkspace` currently assumes `domain.id` is a preset select value; a custom ID needs an explicit selector state and validated adapter rather than an unchecked cast to `GraphPreset`. The generic `drawingPositions` fallback also needs a reviewed two/three-site layout and keyboard/form selection in an eventual implementation. Preserve `square` and `torus` cell-complex presets unchanged; in particular the periodic 2×2 torus has parallel oriented +x/+y bonds and four signed faces, and cannot be produced by six simple-pair checkboxes. This proposed bounded editor would supersede the **UI deferral** in [decision D-024](DECISIONS.md) and the preset-only wording in [specification §3.4](SPECIFICATION.md) when accepted for implementation; it does not supersede the distinct-edge/cell-complex mathematical requirements. Record that decision in those documents in the implementation PR, rather than treating this audit as code that has already shipped.

The desired model page can use a responsive grid: left formula and concise explanation, then physical/numerical drafts; main fixed Run/Pause/Step/Reset/status (or an explicitly different deterministic-computation control); one full-width featured stage; a two-column **zero-to-six** optional-card gallery; collapsible detail/reference; and final collapsible mathematics/exercises/experiment prompts. Existing `ModelFormula`/`ModelNotes`, `ScalarNotes`, field/oscillator math cards and M2 exercises provide content, but they should remain model-specific authored material. A chart may be featured, but the default should show a configuration where one exists. The graph/field display is distinct from the number of physical variables and from the number of gallery cards.

On phones, the feature remains full width; the gallery defaults to one detail card with a compact overview toggle. Card selectors, site/bond selectors, Apply and Reset must stay keyboard/touch operable. “Up to six” refers to **gallery assignments**, not a cap on observables, graph variables or the feature. A gallery may be empty. Duplicate tool types can be allowed for different targets or views, with separate assignment keys and local viewport state.

## Proposed small typed contracts (illustrative, not code)

The types below deliberately do **not** turn every configuration into a number array. `ModelId` describes a mathematical family/measure, `ConcreteSystem` supplies its typed geometry/boundaries/parameters, `NamedExample` adds pedagogical defaults, and `WorkspaceId` describes navigation/session placement. A presentation adapter can expose the same family or example in more than one workspace, but each mounted workspace still owns a separate run unless the user explicitly transfers state.

```ts
type WorkspaceId = 'small' | 'lattice' | 'qm' | 'fields' | 'experiments';
type ModelId =
  | 'zero-d-gaussian' | 'single-spin' | 'binomial-count'
  | 'graph-ising' | 'graph-real-scalar' | 'square-ising'
  | 'ordinary-gaussian-field' | 'mean-zero-gff' | 'harmonic-oscillator';

// Pure, model-specific mathematics. These are separate typed entries, not
// a registry whose State and Parameters collapse into unknown/number[].
interface ModelDefinition<Parameters, State, ObservableId extends string> {
  readonly id: ModelId;
  validate(parameters: Parameters): void;
  action(parameters: Parameters, state: State): number;
  observable(parameters: Parameters, state: State, id: ObservableId): number;
}
interface ConcreteSystem<Configuration> {
  readonly familyId: ModelId;
  // Model-specific typed configuration includes geometry, boundaries and
  // physical couplings; it is not a generic array or a workspace route.
  readonly configuration: Configuration;
}
interface NamedExample<Configuration, RunDefaults, ToolId extends string> {
  readonly id: string;
  readonly system: ConcreteSystem<Configuration>;
  readonly runDefaults: RunDefaults; // typed sampler, seed and schedule
  readonly question: string;
  readonly defaultFeatured: ToolId;
  readonly defaultGallery: readonly ToolId[];
}
interface CatalogPlacement {
  readonly exampleId: string;
  readonly workspaceId: WorkspaceId;
  readonly perspectiveId: string; // e.g. local inspection vs field theory
}

type ExecutionKind = 'monte-carlo' | 'deterministic' | 'physical-time';
type DataNeed =
  | 'current-state' | 'latest-transition' | 'recent-measurements'
  | 'full-segment-aggregates' | 'exact-reference'
  | 'optional-analysis';
type ToolAvailability =
  | { status: 'ready' }
  | { status: 'awaiting-data'; reason: string }
  | { status: 'unsupported'; reason: string };

interface NumericalView<Snapshot, Segment> {
  readonly execution: ExecutionKind;
  readonly snapshot: Snapshot;
  readonly segments: readonly Segment[];
  readonly runId: number;
  readonly version: number;
  // The worker's current state/aggregates remain authoritative.
}
interface ToolDefinition<Id extends string, Context> {
  readonly id: Id; // namespaced and stable, e.g. 'field.spectrum'
  readonly title: string;
  readonly needs: readonly DataNeed[];
  readonly placement: 'featured-and-gallery' | 'gallery' | 'detail';
  availability(context: Context): ToolAvailability;
  // A React adapter renders the tool; pure ModelDefinition never imports it.
}
type ToolAssignment<ToolId extends string> = {
  readonly key: string; // unique instance, even if a tool ID repeats
  readonly toolId: ToolId;
  readonly target?: string;
  readonly collapsed: boolean;
};
type PageAssignments<ToolId extends string> = {
  featured: ToolAssignment<ToolId>;
  gallery: readonly ToolAssignment<ToolId>[]; // length <= 6
};
```

In a real implementation, use `ModelDefinition<GraphIsingParameters, number, GraphIsingObservable>` and `ModelDefinition<GaussianFieldParameters, readonly number[], FieldObservable>` as **separate static entries**. The first receives the preserved `Domain` with edge IDs/faces; the second receives `FieldShape`. A dimer and a frustrated triangle would be two `NamedExample` entries referring to the **same** graph-Ising definition and transition kernels. `oscillatorField(physical)` is an already validated adapter from physical oscillator controls to Gaussian mathematics; its `ModelId` remains `harmonic-oscillator`, so the page can live in QM while reusing the field engine. A Gaussian field could later appear in Small Systems and Lattice Fields through two `CatalogPlacement` entries and perspective-specific tool lists referencing the **same** `fieldAction`/reference module; this does not imply sharing a worker, a configuration URL, or an archive source identity. The six-card limit belongs to `PageAssignments`, not `ModelDefinition`.

The `needs` list is a declaration for explanation and capability checking, **not** an instruction to turn worker accumulation on/off when a card opens. Existing full-segment moments, pair sums, diagnostic rings and bounded histories remain unconditional for the model/run. A future genuinely expensive optional analysis may be computed from a snapshot in a memoized view, or may require a separately versioned explicit request; the latter is a numerical-data contract change with its own tests. The `availability` result should render guidance rather than zeros or invented exact values. The tool renderer may own selection/viewport state but receives read-only numerical context. Draft parameter editing belongs to a separate typed controller with Apply/Reset, never to a read-only tool contract.

### Featured stage, exchange and state identity

Use one static list of tool definitions and one model-specific renderer per page. The feature and gallery contain **assignments**, not cloned tool components. To feature a gallery item, atomically swap its assignment with the featured assignment (or move the old feature to that gallery position); retain each assignment’s unique key, target and viewport choices. Render each assignment in exactly one position at a time. A “choose another featured tool” command can perform the same swap or put the old feature into an empty gallery slot, respecting the six-card cap. The feature itself is mandatory for a model page and may not count toward six optional cards. If the gallery has six cards and a new feature is selected from the library rather than from a card, require an explicit replacement choice; do not silently evict a card. Named-example selection supplies initial assignments without restricting later tool or parameter changes; tab switches preserve local assignments, as M4c0 already preserves mounted state.

React placement can remount a renderer even with a preserved assignment key. `FieldSpectrum` currently owns momentum selection locally; `IsingMatrix` owns connected/raw toggle; `ToolDeck` owns card state; several plots own viewport navigation. A migration must hoist only **presentation state that should survive a feature/card swap** into the assignment or a keyed adapter, and test that remounting does not send numerical commands. Do not duplicate the renderer in both positions simply to avoid remounts: duplicate mounted transfer cards could run the same expensive analysis, and duplicate local selectors would diverge.

## Execution, editing and data invariants

1. **Drafts are not current science.** `GraphWorkspace` and `ScalarWorkspace` combine SVG selection, current-state inspection and numeric draft editing. The draft table belongs in the sidebar or collapsible detail with an explicit Apply; it must display applied versus draft values. Selecting a vertex/edge, momentum, site pair, window, color scale or camera/viewport is display-only and must not advance a client or RNG. Pointer and numeric selectors must reach the same selection state.
2. **Support and topology changes keep their present lifecycle.** Small model-family or graph-topology changes start a seeded session; compatible graph couplings/site fields, scalar potentials and samplers start new measurement segments while retaining state/RNG as implemented. Large Ising dimensions/boundaries start a session; T/J/h/sampler/cadence changes preserve spins/RNG, recompute H and restart segment warm-up. Field shape or ordinary↔mean-zero support starts a session; fixed-support coefficient/sampler changes start a segment. Oscillator N or model switch starts a session; β/ω/sampler changes at fixed N preserve path/RNG and begin a segment. Reset clears history and uses the stated seed policy. Read `SimulationRun.changeSettings`, `ScalarRun.changeSettings`, `LatticeRun.changeSettings`, `FieldRun.changeSettings` before touching Apply wiring.
3. **Snapshots are versioned, segment-scoped and bounded.** A view must not pool measurements across measures or infer missing history from aggregate moments. Current state may not belong to a historical segment. Histograms/checkpoints/full pair products and recent vectors have different coverage. Display updates, render rate, card order and navigation must not change seeded transitions, warm-up, stride or archive captures. Preserve the one-batch-in-flight client boundaries and separate QM/Fields workers (`SimulationClient`, `LatticeClient`, `FieldClient`, `useField`).
4. **Units and quality travel with data.** `DataNeed` plus model-specific labels should distinguish action `S`, physical H/e, count K, m/|m|, site amplitude, Fourier momentum, Euclidean t, update number, nominal sweep and observation lag. The M3a exact and empirical τ must retain matching cadence; recent-window ESS/SE must not be pasted onto a full-segment mean. Exact, finite-grid quadrature, continuum theory and sampled/provisional values need distinct statuses. Open/mixed spatial correlations stay raw; mean-zero fixed-neighbor conditional stays unavailable.
5. **Execution categories are explicit.** Today every live model samples a Gibbs measure, while exact references are pure computations. A later deterministic solver might have compute/progress/cancel rather than Run/Step. Physical-time evolution would need a physical-time coordinate and integrator-state protocol. `ExecutionKind` is a presentation discriminant for those future controls; it does **not** retrofit Monte Carlo counters into physical time or implement new dynamics.

## Explicit non-standardization and deferred work

- Do not merge `Domain`, `IndexedLattice` and `FieldShape` into one graph representation. Edge IDs, parallel bonds, oriented faces, row-major indices and the oscillator's Euclidean coordinate each serve different mathematics.
- Do not require every model to expose a potential curve, graph editor, acceptance percentage, Fourier spectrum, exact partition, or six populated cards. Show a reasoned unavailable state when a user selects a scientifically inapplicable tool.
- Do not unify Gibbs action and physical Hamiltonian units, independent draws and local-update sweeps, Euclidean coordinate time and Monte Carlo update time, or full-segment aggregates and bounded recent records.
- Do not make tool visibility control measurement accumulation or let a React registry own RNG, worker stepping, warm-up or archive provenance. Avoid a dynamic plugin framework and new universal plotting dependency for this migration.
- Do not redesign saved experiment schemas, promise persistence of presentation choices, add a backend, or copy historical configurations into a live session implicitly.
- Do not encode a fixed tab in a mathematical model, call each named example a new model family, or make one example's sampler/display defaults into immutable physical parameters.
- Fermionic/Grassmann or occupation-state interfaces, Hubbard models, real-time dynamics, gauge/link/plaquette dynamics, interacting double-well/φ⁴ paths and HMC require their own validated domain, execution and reference decisions. This audit reserves space for them; it does not implement or constrain their scientific representations.
